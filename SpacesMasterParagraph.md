Spaces (internally "SpaceBook") is a production room-, resource-, and approval-workflow platform that I designed, architected, and built end-to-end as the sole application engineer for the UBC Faculty of Medicine, replacing an aging FM:Systems Resource Scheduler deployment the faculty had depended on for roughly twenty years, together with two in-house UBC applications - Room Finder and Advanced Booking Manager - built to support and work around it. I owned every layer of the system and every decision inside it: the relational data model, the domain and business logic, the REST and server-action API surface, the entire frontend and design system, the AWS serverless infrastructure, the security and identity model, the test strategy, the technical documentation, and the stakeholder conversations that determined what got built and in what order. Over roughly six months I took it from an empty repository to a live system of approximately 113,000 lines of TypeScript across 551 files, delivered through 550+ commits and 220+ reviewed pull requests, comprising 35 application routes, 34 REST API endpoints, 30 server-action modules, and 132 React components; it manages a catalogue of 400+ bookable rooms and resources across distributed sites province-wide in British Columbia, currently runs in production with a pilot cohort of faculty staff, and is scheduled for full cutover from the legacy system in January. The frontend is Next.js 16 on the App Router with React 19 Server Components, written in TypeScript under strict mode and styled with Tailwind CSS v4 and shadcn/ui over Radix UI primitives, with a 31-component internal design system, dark-mode theming via next-themes, form handling through React Hook Form with Zod schema validation shared between client and server, and a deep component layer that includes a multi-step booking wizard, drag-to-create availability calendars built on dnd-kit, a TipTap rich-text editor, Leaflet and Google Maps location views, Photo Sphere Viewer 360° room panoramas, a cmdk command palette, date-fns and date-holidays scheduling utilities, driver.js guided product tours for onboarding, and accessibility work (semantic ARIA roles, keyboard navigation, screen-reader labelling) applied across the surface. The backend is a modular monolith running on Node.js 24, using Prisma ORM against MySQL 8 on Amazon RDS, with business logic isolated into domain modules behind server actions and API routes, transactional writes wrapped in Prisma interactive transactions, and a schema I designed from scratch spanning 49 data models and 96 committed migrations covering resources and their taxonomy, multi-room bookings, recurring series, a nine-state booking lifecycle, configurable multi-stage approval chains, exclusively-scheduled Zoom licences and equipment assets, a transactional email outbox, and an append-only audit log. I deployed it on AWS, containerizing the application with a multi-stage Docker build against the Next.js standalone output and running it on ECS Fargate behind images published to Amazon ECR — a migration I performed off an earlier AWS Amplify deployment to gain control over the runtime — with RDS over enforced TLS, S3 and CloudFront for resource media served through presigned uploads and signed delivery URLs, API Gateway fronting several Lambda functions I wrote (an email dispatch worker, an SES inbound forwarder, a Keycloak JWT custom authorizer, a scheduled dispatch cron, and an automated Secrets Manager rotation handler), SQS for asynchronous message delivery, IAM least-privilege policies, and CloudWatch RUM for real-user performance and error telemetry, alongside a /api/health liveness endpoint for container health checks. Delivery runs through a GitHub Actions CI/CD pipeline on self-hosted runners that builds with BuildKit caching, generates an SBOM, gates on Trivy container scanning and npm audit dependency scanning, and deploys digest-pinned images to ECS so that every release is immutable and traceable. The hardest engineering was correctness under concurrency and under time: I wrote a conflict-detection engine that reasons about per-resource setup and cleanup buffer windows, scheduled maintenance blocks, and mutually-exclusive "separation groups" of rooms that physically cannot be occupied simultaneously, then extended the same guarantees to pooled Zoom licences and portable equipment so a room booking and an asset booking can never silently double-allocate; I built a custom recurrence engine instead of adopting RRULE, because real faculty scheduling required monthly nth-weekday and end-of-month clamping strategies, per-occurrence room and time overrides, partial series cancellation, and series extension, and I pinned all scheduling arithmetic to America/Vancouver with explicit handling of DST boundaries including British Columbia's 2026 transition to permanent UTC-7, forcing the whole test suite to execute in that timezone so regressions surface in CI rather than in someone's calendar; and I implemented the approval engine as a state machine over admin-configurable chains supporting both named-user and role-based approvers, snapshotted onto each booking at submission so an admin editing a chain cannot corrupt requests already in flight, layered with advanced-booking submission rounds for contested teaching spaces, resource-policy review gates, and optimistic concurrency control with retry on Prisma write-conflict errors and bounded parallelism so batch-approving hundreds of bookings degrades gracefully instead of deadlocking. For delivery reliability I replaced fire-and-forget email with a transactional outbox pattern: messages are committed to the database in the same transaction as the business write, dispatched event-driven through SQS to a Lambda worker backed by SES, deduplicated by idempotency key, retried with exponential backoff, reconciled against SES bounce and complaint webhooks, and replayable by an administrator from the UI, with per-resource templates stored in the database and editable in-product rather than hardcoded — all behind a provider abstraction so the transport can be swapped without touching business logic. Identity federates to institutional Keycloak SSO over OIDC/OAuth 2.0 through NextAuth v5 (with a bcrypt credentials fallback), using JWT sessions with OIDC token sets persisted server-side to keep cookies under browser size limits, a seven-role RBAC model supplemented by per-user capability flags for job functions that didn't map cleanly onto a role, route-level middleware guards backed by server-side authorization re-checks as defense in depth, hardened response headers including CSP and HSTS, and a 60-minute idle session timeout implemented specifically to satisfy a UBC IT security control. On top of the core I shipped the operational surface the faculty actually runs on: a 22-route administrative suite with global booking search and CSV export, a live resource-availability timeline, maintenance-window scheduling, resource taxonomy and visibility-group management, database-backed email template editing with a delivery log, announcements, and a super-admin audit trail rendering field-level change diffs, written non-blocking through Next.js after() so observability never slows a user action or fails a booking — plus the adoption features that drove real usage, including Panopto lecture-capture folder synchronization, ICS calendar export for single and bulk bookings, public QR-code room availability pages, shareable tokenized room links, saved and shared room presets, one-click rebooking, and an optional OpenAI-powered bulk-paste importer that normalizes unstructured pasted schedules into validated booking records behind a feature flag. I backed the domain logic with 48 test suites and roughly 745 assertions concentrated where silent bugs are most expensive — conflicts, recurrence, timezone arithmetic, and approval gating — enforced type safety and linting through tsc and ESLint as pre-deploy gates, applied React and Next.js performance practices including route-level ISR, dynamic imports and code splitting for heavy client components, and wrote 32 architecture and feature documents so the platform could survive handoff, including a full walkthrough I presented to engineering managers, senior developers, solution architects, and cloud engineers. Beyond the code I gathered requirements directly from faculty stakeholders and translated a PRD into a delivery roadmap, ran the phased pilot rollout and fed user feedback back into the product, built the migration tooling that reads reservations out of the legacy Resource Scheduler REST API and imports them into the new schema, reviewed and merged contributions from a DevOps collaborator and other developers on the team, and established the repository's engineering standards including codified AI-assisted development workflows (agent rules, skills, and conventions checked into the repo) that kept a codebase this size consistent while being maintained by one person. The Faculty has since offered me a continuing part-time engineering role to carry the platform through full migration and beyond.

## Why the project existed at all

The Resource Coordinating Team - the group responsible for managing rooms, bookings, and shared resources across the Faculty - had been running on FM:Systems Resource Scheduler for roughly twenty years, supplemented by two applications UBC developed in-house - Room Finder and Advanced Booking Manager (ABM) - to cover what Resource Scheduler could not do. Spaces replaces all three; full cutover is planned and the team is currently in a transition phase. The product was shaped for hotel-style reservation management rather than for teaching rooms, clinical spaces, and shared equipment, so the fit was poor from the beginning and degraded over time: the team accumulated a large body of manual workarounds for requirements the software could not express. The situation worsened when the vendor was acquired and effective support ended, leaving the Faculty paying a substantial annual licence for a legacy system with no developer support behind it. They had been actively looking for a replacement for years without success, because the Faculty of Medicine's requirements - its approval hierarchies, its contested teaching spaces, its province-wide distributed sites - are specific enough that no off-the-shelf product addresses them, and a bespoke internal build had always been scoped as a multi-engineer, multi-year, heavily-processed effort that was too expensive to justify. My manager had observed how quickly I was able to move using AI-assisted development and suggested I attempt a prototype rather than continue the search. The prototype became the funded project.

## Velocity, and how it was actually achieved

I started the project in February 2026 and had it running in production roughly six months later - an unusual timeline for a system of this size in a university IT environment, and one that has drawn repeated comment from stakeholders inside the Faculty. The velocity came from treating AI-assisted development as a disciplined engineering practice rather than as autocomplete: I worked primarily in Cursor, and I codified the repository's engineering standards into agent rules, reusable skills, and conventions checked into version control alongside the code, so that AI-assisted work always started from the project's real architecture and constraints instead of generic defaults. This is what kept naming, error handling, data-access patterns, and test structure uniform across 551 files without a team's worth of code review pressure to enforce it.

It is worth being precise about what this was and was not. This was not a one-shot generation problem and could not have been vibe-coded. The domain is niche, and the requirements lived largely in the heads of people who had spent two decades working around inadequate software; extracting them required many rounds of building, demoing, and correcting against real users. What AI leverage bought was iteration speed - the ability to absorb feedback from a demo and have the correction in front of the team within days - which on a domain-heavy project compounds far more than raw typing speed. The guardrails around it were deliberately mechanical, because the characteristic failure mode of generated code is that it looks correct and is subtly wrong, which is precisely what a booking system cannot tolerate: tsc and ESLint as hard pre-deploy gates, 48 test suites concentrated on conflicts, recurrence, timezone arithmetic and approval gating, 220+ self-reviewed pull requests, and Trivy container and dependency scanning in CI. The system also passed UBC's institutional security review, a materially less forgiving audit than a passing test suite.

## Reception and organizational impact

The project has been received as a significant win inside the Faculty. I present updates and demos on a weekly cadence and consistently receive direct positive feedback from stakeholders and end users. The platform improves both sides of the transaction simultaneously, which is the main reason for that reception: the Resource Coordinating Team gets approval workflows, conflict detection, and audit trails that match how they actually work, while faculty and staff booking a room get a process that no longer requires institutional knowledge of workarounds. Beyond the product itself, the delivery approach has become an internal reference point - colleagues have asked how the timeline was achieved, and other teams have begun evaluating the same AI-assisted methods for modernizing their own internal tooling.
